## 现在三个人分别做什么

### A：交接基础版本并准备章节图谱

1. 阅读 01 的验证记录，向 B、C 交接当前可运行基础版本和启动说明。
2. 三人在各自电脑按 README 安装和启动，确认自己的环境能导入、阅读资料；已有验证结果用于对照。
3. 从共享仓库取得 `main`，各自使用任务分支开发。向 B 提供真实教材小节及其出处记录，教材原文通过约定的资料渠道交接。
4. 与 B 确认 02 要输出的知识版本和图谱接口；B 实现 02 时，先准备 03 的界面交互及验证案例。
5. 02 集成后完成 03。此后你推进 08，B 推进 04，C 推进 07，三条功能主线可以并行。

### B：先验证模型接入，再接首次整理

1. 01 已就绪，可从共享 `main` 创建 02 分支，先完成 Flash 适配器的最小验证：真实 Responses 请求、结构化输出、思考模式、流式事件、截断及错误分类。
2. 与 A 对齐资料读取和原文片段约定。模型只能引用程序给出的片段标识，不能生成自称真实的行号或页码。
3. 接入 02，以一小节真实教材贯通完整流程；同时交付后续问答与路线能够读取的版本化知识接口。
4. 把 02 的知识与任务模块交接给 A，再推进 04 → 05 → 06；08 和 05 都完成后推进 11。
5. 准备问答和笔记样例供 C 验收，尤其是跨知识点问题、资料不足和拓展标记。

### C：立即准备验收材料和路线案例

1. 从约定教材范围建立约 20 个问题的验收表，记录题目、可接受要点、原文支持位置或资料不足原因。可以立即做这项工作，不必等待应用完成。
2. 准备学习路线案例：普通前置链、分支、循环、缺口、包含和对比关系混入。先用明确标识的测试数据表达预期结果。
3. 与 A、B 对齐知识快照读取约定，在独立分支准备路线计算和界面。03 就绪后接入并验收 07。
4. 前置条件满足后，分别推进 12、13、14，不要求机械地逐个等待编号。
5. 负责最终目标电脑的 15。A、B 分别处理验收中属于其主责范围的问题，C 不承担修复所有模块的责任。

前置任务未完成时，可以准备适配器、算法案例、界面组件和测试数据；基于模拟数据的局部验证不能代替真实集成验收，也不能据此勾选整张任务。

## 三次关键交接

### 01 → 02：资料与来源

A 向 B 提供可运行版本及以下事实：

- 如何创建课程、导入资料、读取章节和原文片段。
- 课程、资料、章节及片段的稳定标识和归属检查。
- 行号的计算规则、起止边界及原始 Markdown 的读取方式。
- 一个真实教材小节及独立出处记录；原文不被自动清洗覆盖。
- 执行过的检查、当前未通过项和启动命令。

当前 01 已实现的接口可通过运行后端的 OpenAPI 查看。B 使用这些公开接口或资料模块公开方法，不直接修改原文记录。

### 02 → 03／04／07：版本化课程知识

B 在交接记录中固定以下契约，再交由三人共同使用：

- 课程标识、知识版本标识、候选与已发布状态，以及读取指定版本的方式。
- 章节和知识点节点；包含、前置、对比关系及方向。
- 稳定知识点身份、名称、别名和跨章节归属。
- 知识点页面、原文片段引用、资料依据与推断标记。
- 整理任务的发起、进度、失败和结果读取方式。

接口改动需附真实返回示例和兼容说明。问答、路线和图谱通过同一份已发布知识读取，避免各做一份独立知识数据。

### 08／11 → 12／13：更新与个人成果

A、B 向 C 共同提供：

- 当前版本切换与指定旧版本读取的方式。
- 追加资料后的变化摘要、冲突说明和原文依据。
- 个人笔记的读取、引用、拓展标记及来源变化提示。
- 反馈整理的复用入口，以及导出时固定版本和笔记内容的方式。

C 的纠错和导出通过这些接口工作，不直接更新知识或笔记的数据表。

| 应用入口、共享类型、依赖文件、数据迁移 | A 协调 | 所有者先沟通变更，再由一条分支集成，避免多人同时改锁文件 |

现有前端集中在一个入口中。开始多功能并行前，由 A 统一拆出应用外壳和功能区域；B、C 在各自功能目录实现，连接外壳的改动集中合并。目录的具体命名由这一轮实现确定，不额外建立无用抽象。

## Git 和数据约定

1. 每人使用自己的代码副本、虚拟环境、依赖目录和数据目录。不要让三台电脑共同写同一个 SQLite 文件。
2. 使用共享 `main` 保存通过当前阶段检查的代码，每张任务从所需前置已合并的版本创建分支，例如 `ticket/04-course-questions`。
3. 前置尚未合并时的准备工作放在自己的准备分支，注明使用的接口假设；正式验收前与真实接口集成。
4. 一个任务交付一个可审查的改动，说明实现行为、检查结果、迁移影响和剩余限制。A 负责协调合并，保持各成员及时取得最新基础版本。
5. 课程数据、教材正文、模型密钥和本机依赖不作为源码提交；共享短测试材料时保留真实出处。每人在后端配置自己的模型调用凭据，前端不持有密钥。
6. 数据结构变更随代码交付迁移方法，验证已有课程资料仍能读取，不能要求其他人清空数据来掩盖不兼容。
7. 主动同步跨模块接口变化，避免通过直接访问别人的数据库表或修改导出文件绕过约定。

## 每次交付要带什么

- 任务编号、代码分支或提交，以及完成的用户操作。
- 可复现的启动和验证步骤。
- 已通过和未通过的验收条件，附真实结果。
- 如有接口变更：请求、响应、错误状态和知识版本约定。
- 如有样本：原文出处，说明是真实资料还是故障测试数据。
- 下一位成员可以据此开始哪些任务。

建议交叉审查：A 审查 B，B 审查 C，C 审查 A；涉及知识版本或来源定位的改动，再请 A、B 共同核对。
