## 三次关键交接

### 01 → 02：资料与来源

A 向 B 提供可运行版本及以下事实：

- 如何创建课程、导入资料、读取章节和原文片段。

- 执行过的检查、当前未通过项和启动命令。

当前 01 已实现的接口可通过运行后端的 OpenAPI 查看。B 使用这些公开接口或资料模块公开方法，不直接修改原文记录。

### 02 → 03／04／07：版本化课程知识

B 在交接记录中固定以下契约，再交由三人共同使用：

- 课程标识、知识版本标识、候选与已发布状态，以及读取指定版本的方式。
- 章节和知识点节点；包含、前置、对比关系及方向。
- 稳定知识点身份、名称、别名和跨章节归属。
- 知识点页面、原文片段引用、资料依据与推断标记。
- 整理任务的发起、进度、失败和结果读取方式。

接口改动需附真实返回示例和兼容说明。问答、路线和图谱通过同一份已发布知识读取，避免各做一份独立知识数据。

### 08／11 → 12／13：更新与个人成果

A、B 向 C 共同提供：

- 当前版本切换与指定旧版本读取的方式。
- 追加资料后的变化摘要、冲突说明和原文依据。
- 个人笔记的读取、引用、拓展标记及来源变化提示。
- 反馈整理的复用入口，以及导出时固定版本和笔记内容的方式。

C 的纠错和导出通过这些接口工作，不直接更新知识或笔记的数据表。

## Git 和数据约定

1. 每人使用自己的代码副本、虚拟环境、依赖目录和数据目录。不要让三台电脑共同写同一个 SQLite 文件。
2. 使用共享 `main` 保存通过当前阶段检查的代码，每张任务从所需前置已合并的版本创建分支，例如 `ticket/04-course-questions`。
3. 前置尚未合并时的准备工作放在自己的准备分支，注明使用的接口假设；正式验收前与真实接口集成。
4. 一个任务交付一个可审查的改动，说明实现行为、检查结果、迁移影响和剩余限制。A 负责协调合并，保持各成员及时取得最新基础版本。
5. 指定的共享教材和短样本保存在 `materials/`，保留原文和真实出处。应用运行数据、SQLite 数据库、模型密钥和本机依赖不提交。每人在后端配置自己的模型调用凭据，前端不持有密钥。
6. 数据结构变更随代码交付迁移方法，验证已有课程资料仍能读取，不能要求其他人清空数据来掩盖不兼容。
7. 主动同步跨模块接口变化，避免通过直接访问别人的数据库表或修改导出文件绕过约定。

## 每次交付要带什么

- 任务编号、代码分支或提交，以及完成的用户操作。
- 可复现的启动和验证步骤。
- 已通过和未通过的验收条件，附真实结果。
- 如有接口变更：请求、响应、错误状态和知识版本约定。
- 如有样本：原文出处，说明是真实资料还是故障测试数据。
- 下一位成员可以据此开始哪些任务。

建议交叉审查：A 审查 B，B 审查 C，C 审查 A；涉及知识版本或来源定位的改动，再请 A、B 共同核对。
